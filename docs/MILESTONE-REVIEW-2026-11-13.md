# 전체 마일스톤·코드량 재점검 — 2026-11-13

기준: 공개 main 7ecddfe / Preview0.3.101. 기능 구현을 중지하고 현재 소스·M1 완료 감사·확정 명세·6단계/1단계 계획을 대조한 계획 문서다. 이 문서는 새 기능 구현이나 완료 판정이 아니다. 구조·문서·주요 진입점의 정적 점검이며65항목 전체의 모든 실행 경로를 새로 완료 감사한 것은 아니다.

## 먼저 바꿔야 할 진행 관리

- 현재 제품 C#은 149파일/19,712 물리 줄(비어 있지 않은 줄19,082), 그중 Contracts137파일/18,575줄이다. 테스트는107파일/9,970줄이다. XML은49파일/1,818줄이다. bin/obj/생성 코드·게임 역컴파일·문서·DLL·패키지는 제외했다. 물리 줄은 주석/빈 줄을 포함하므로 실행문 수가 아니다. 기존 규칙/테스트는 반복문과 압축된 표현이 있어 다른 파일의 물리 줄 수와 기능량을 직접 비교할 수 없다. 전체 인벤토리는 함께 저장한 JSON의 source_census에 있다.
- M1은 기존 10/10 완료 근거를 유지한다. M2는 원 주민·임상·의료·지도·기본 재산·현재 승인·두 구간 인계·귀족 민간인 실행이 이미 부분 연결되어 있다. M2 0/18은 ‘아무 코드도 없음’이 아니라 옛 작업군 전체 완료 조건 미충족을 뜻한다.
- 과거 31.5/80/95/90/100/70%는 노력의 역사적 추정이다. 특히31.5%는 고정식65+35×완료점수에서 파생됐으며 이번 코드 실측으로 검증한 잔여율이 아니다. 그대로 정확한 현재 진척률처럼 보고하지 않는다.
- 기존 단계/작업군 범위와 배점은 축소하지 않는다. 아래 M2 세부 배점 합은18이며 다른 M3~M9도 기존 합계를 유지한다. **세부 점진 배점은 검토안**이며 합의·완료 근거 재검수 전에는 기존 10/100 및 M2 0/18을 소급 변경하지 않는다.
- 앞으로 각 항목에 실제 진입점/변경 파일/저장 필드/복구 함수/남은 조합/검사 근거를 연결한다. 버전·테스트 수·작성 줄 수로 완료 점수를 주지 않는다.

## 견적 읽는 법

단위는 C# 작성 또는 실질 수정 대상 줄 수다. 단순 이동·포맷 변경·자동 생성·의도적 중복은 제외한다. 기존 코드를 고쳐 쓰는 양도 포함하므로 최종 저장소 줄 수의 순증가와 다르다. 테스트 코드는 별도이며 XML/영한 문구·커버/설치 문서·API 조사 시간은 줄 수에 포함하지 않는다. 테스트 분량은 아직 개별 fixture 설계 전이므로 제품 코드 하한의50%~상한의85%를50줄 단위로 반올림한 초기 예산이다. 독립적으로 실측한 테스트 견적이 아니며 기존 fixture 재사용에 따라 크게 달라진다. 각 범위는 독립 실행+실제 적용+저장/중단 복구를 포함한 계획 추정이지 견적 보장이나 구현 지시가 아니다.

일반 항목은 오차 약±40~60%를 예상한다. native 진행 작업·노예·소실·마지막 세력·외부 제공자 API는 확인 결과에 따라 상한의2배 이상이 될 수 있다. 숫자를 맞추기 위해 코드를 늘리지 않는다. 공용 보존/권한/journal 기반은 최초 소유 항목에만, 후속 항목은 연결 차이만 계산했다.

## 실제 코드 경계와 중복 계산 방지

- Honor.Contracts.Rules: 계약/채무/현재 승인·증거/단계 전이와 복원 검증. 엔진 객체를 만들거나 실제 소속을 바꾸지 않는다.
- Honor.Contracts.Preview: 현 객체·정치 권한 검토, native executor, 원 참조 Scribe, UI/실행 coordinator. 각 기능은 current review→사전 staging→원본 재검토→실행 전 기록→정상 반환→보존 검증→완료→명시 복구 경로를 가져야 한다.
- 공통 계약/공납/관계·현재 의결은 기존 모듈을 재사용한다. 예: M2.8은 물리 누락/소실 분류를, M7은 계약·계층 정리를 소유한다. M2.4는 작업 보존을, M3.1은 수술 지시/결박 자원을 소유한다. M1의 서약/승계를 C8에서 재개발하지 않는다.
- RoyalResidents/CustodyAgreements/ResidentExecution/MapAssetRecords를 동일한 데이터 소스로 유지한다. 기능별 새 대형 ledger를 무조건 복제하지 않고 필요할 때만 원 증거/호출/권한 경계를 분리한다.
- 1.6/net472와1.7/net10은 별도 빌드/검토 대상이다. ‘빌드 통과’는 미확인 native 몸체에 대한 실행 허가가 아니다. 현재 새 왕실 실행은 감사한5005에 한정되어 있으므로 완전한1.6 지원 비용을 R2에 따로 남긴다.

## 개발 선행과 통합 완료의 구분

기존 작업군 경계에는 중복 요구가 있다. 구현 책임은 유지하되 선행 개발과 최종 교차 검사를 나눴다. 예를 들어 M2.7은 M7.1의 양성 소실 증거를 소비하며, M7.1은 M2.1 원 객체 식별만 선행한다. M2.3은 개인 왕실 권리 기반을 먼저 제공하고 M4가 지도자 승계에 재사용한다. M6.3은 M7.1/2의 근거·정리를 소비하고 최종 혼합 귀환은 M7.3에서 닫는다.

따라서 **M2의 모든 조합을 먼저 끝낸 다음 M3로 넘어가는 직선 순서는 적절하지 않다.** M2의 원본 보존 기반과 남은 소유 기능을 만든 뒤 M3/4/5/6/7의 담당 부분을 통합하고 M2.10에서 전체 완료를 감사한다. 이는 M2 완료 조건 삭제가 아니라 기존 교차 요구를 명시하는 것이다. JSON의 integrates_with는 후속 교차 검사를 뜻하며 새로운 중복 구현 예산이 아니다.

## 작업 순서

1. M2.1/M2.2를 기존 실제 경로와 대조하고 M2의 지원/미지원 매트릭스를 확정 명세에서 추출한다. 기존 데이터 보호 조건이나 작업군 분모를 줄이지 않는다.
2. M2.3 개인 왕실 권리 → M3.1/2/3과 연결할 원본·현재 동의 경계 → M2.4 작업·예약 → M2.5 집단/관리 권리 → M2.6 보관함 순으로 직접 이전 기반을 닫는다. 서로 독립인 조사/fixture는 묶을 수 있으나 상충 native 집행은 동시에 하지 않는다.
3. M7.1의 실제 소실 증거와 M2.7/8을 결합해 원 객체 귀환 재개와 확정 영구 소실의 합법적 후속 처리를 구분한다. 물리적으로 파괴된 Pawn/Map/Thing을 같은 객체로 임의 재생성하는 것을 복구 목표로 삼지 않는다. 미확인 누락은 확정 소실도 아니다.
4. M4 지도자 → M5 독립 → M6 이적 → M7 전체 혼합 복구 → M8 합병 → M9 통합 감사를 마무리한다. 개별 기능은 항상 저장/복구·영한·양 타깃 확인까지 포함한다.
5. 이후 E→W→P→C의 흐름을 연결하고, R의 저장/호환/용량은 각 단계에서 병행한다. 기존5개 모드 명세 차이와 정식6개 모드 통합 감사도 별도 R5로 수행한다.
